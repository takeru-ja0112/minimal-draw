# お手軽スタート機能 実装計画

## 0. 参照元

- 元ネタ: [doc/2026_08_23ランダムゲームの開始ロジック.md](../doc/2026_08_23ランダムゲームの開始ロジック.md)

## 1. 背景・目的

現状のルーム画面（[components/pages/RoomPage.tsx](../components/pages/RoomPage.tsx)）では、参加者が「絵を描く人はこちら」「お題を答える人はこちら」の2つのボタンから自分の役割を各自選んで押す必要があり、誰が回答者になるかをメンバー間で相談してから動く必要がある。これによりゲーム開始までの意思決定コストが高い。

これを解消するため、ゲームマスター（ルーム作成者）が1ボタン（「お手軽スタート」）を押すだけで、回答者をランダム決定し、それ以外を描く人としてゲームを開始できるようにする。

## 3. 設計方針（重要な意思決定）

### 3.1 「描く人」の明示登録テーブルは追加しない

要件文には「回答者以外のメンバーIDを絵を描く人として登録する」とあるが、実装上は **`answer_id` 以外は全員「描く人」** という暗黙定義で十分に要件を満たせる。理由:

- 現行の `AnswerPage` の役割判定（`checkAnswerRole`）も「`answer_id` と自分の `userId` が一致するか」の一点のみで行っている。
- `DrawPage` には元々役割チェック自体が無く、誰でもアクセス・保存できる設計。
- 新規テーブル・カラムを増やすと、退室・再入室時の整合性維持（誰が「描く人」から外れたか等）という余計な状態管理が発生する。

→ 追加のDBスキーマ変更は不要。「回答者を `answer_id` にセットし、ステータスを `DRAWING` にする」だけで、それ以外の全員が結果的に「描く人」として扱われる。

### 3.2 メンバー一覧取得は Presence をルーム画面に引き上げて共有する

`getRoomMembers` はDBクエリではなく、既存の [usePresence](../hooks/usePresence.ts) （Supabase Realtime Presence）をそのまま「今ルームに実際にいる人」の情報源として使う。`Point` テーブルは退室者も残り続けるため、ランダム抽選対象としては不適切。

現状 `usePresence` は `AccessUser.tsx` の内部でのみ呼ばれているため、**`RoomPage.tsx` に引き上げて `users` を `AccessUser` に props で渡す**形にリファクタリングする（Presence channel の二重接続を避けるため）。

### 3.3 自動遷移と「バック操作で取りこぼした場合の復帰」は同一ロジックに統合する

`useStatus(roomId)` は元々マウント時に必ず1回 `fetchRoomStatus()` でDBの最新状態を取得し、以後はリアルタイム購読で更新される。つまり「ステータス変化をリアルタイムで検知する」ことと「戻ってきた時に現在の状態を検知する」ことは、**このフックの中では同じ `{status, answerId}` の更新として現れる**。

よって新規に作るのは1つだけ:

> `RoomPage` で `status !== 'WAITING'` になった（初回マウント時点で既にそうだった場合を含む）ら、`answerId === 自分のuserId` かどうかで行き先を決め、アナウンス（トースト）を出してから `router.push` する `useEffect`

これで「リアルタイムで即座に動いた場合」と「バック操作で戻ってきて気づく場合」の両方をカバーできる。

### 3.4 ゲームマスター判定

`Room.created_by_userId` を `page.tsx` から `RoomPage` に `creatorId` として渡し、`localStorage` の `drawing_app_user_id`（`lib/user.ts` の `getUserId()`）と比較する。一致しなければボタン押下時に `showToast('ルーム作成者のみが始めることができます。', { variant: 'error' })` を出して処理を中断する。ボタン自体は非表示にせず、誰にでも見せた上で押下時にガードする（既存の `AnswerConfirmModal` 等のUXパターンに合わせる）。

### 3.5 `setStatusRoom` のタイポ型は今回のスコープでは触らない

`'WATING' | 'DRAWING' | ...` のタイポは既知の技術的負債だが、今回の実装では `'DRAWING'` のみを使うため実害はない。別チケットとして切り出すことを推奨し、本計画では変更しない。

## 4. 実装ステップ

### Step 1: サーバーアクション追加（`app/room/[id]/action.ts`）

`confirmAnswerer`（[hooks/RoomPage/useRoom.ts](../hooks/RoomPage/useRoom.ts)）と同様の一連の更新を、**任意のメンバーID**を回答者として指定できる形でまとめた関数を追加する。

```ts
// app/room/[id]/action.ts に追加
/**
 * お手軽スタート: ランダムに決定した回答者IDでゲームを開始する
 */
export async function startQuickGame(roomId: string, answererId: string) {
  try {
    await prisma.drawing.deleteMany({ where: { room_id: roomId } });
    await ensureUser(answererId); // 既存の import に ensureUser を追加

    const data = await prisma.room.update({
      where: { id: roomId },
      data: {
        answer_id: answererId,
        status: 'DRAWING',
      },
    });

    return { success: true, error: null, data };
  } catch (error) {
    console.error('Unexpected error during quick start:', error);
    return { success: false, error: 'Failed to start quick game', data: null };
  }
}
```

- `setdbAnswer` を使い回さず新規に1トランザクション的な関数にまとめる理由: `setdbAnswer` は「既に `answer_id` がセットされていたら失敗する」ガードがあり、かつ `answer_id` セットと `status` 更新が別呼び出し（`confirmAnswerer` は両方 await せず fire-and-forget）になっていて、他クライアントから見て一瞬 `status=DRAWING` かつ `answer_id=null` の状態が見える競合が起きうる。お手軽スタートでは開始直後の役割判定が特に重要なため、**1つの `prisma.room.update` で `answer_id` と `status` を同時に更新**し、この競合を構造的に避ける。
- `setdbAnswerInput` / `setdbAnswerResult` のリセットも `confirmAnswerer` 同様に必要か確認し、必要なら追加（前回のゲームの回答欄・結果が残っている場合があるため、`resetRoomSettings` と同様に含めることを推奨）。

### Step 2: `page.tsx` から `creatorId` を渡す

[app/room/[id]/page.tsx](../app/room/[id]/page.tsx) の `getInfoRoom` 結果には既に `created_by_userId` が含まれているので、`RoomPage` への props に追加する。

```tsx
const creatorId = res.success && res.data ? res.data.created_by_userId ?? '' : '';
return <RoomPage title={title} shortId={shortId} scores={sordScores} creatorId={creatorId} />
```

`RoomPage` の props 型にも `creatorId: string` を追加。

### Step 3: `usePresence` を `RoomPage` に引き上げ

- `RoomPage.tsx` 側で `const user = getOrCreateUser(); const { users } = usePresence(roomId, user.id, user.username);` を呼ぶ。
- `AccessUser` の props を `{ roomId }` → `{ users }` に変更し、内部の `usePresence` 呼び出しを削除。
- これで `RoomPage` 側でもメンバー一覧（Presenceの `users: {user_id, user_name, joined_at}[]`）が使えるようになる。

### Step 4: `useRoom.ts` に `handleQuickStart` を追加

```ts
const handleQuickStart = async (members: { user_id: string }[]) => {
  if (members.length === 0) {
    showToast('ルームに参加者がいません', { variant: 'error' });
    return;
  }
  const randomMember = members[Math.floor(Math.random() * members.length)];
  const result = await startQuickGame(roomId, randomMember.user_id);
  if (!result.success) {
    showToast('ゲームの開始に失敗しました', { variant: 'error' });
  }
  // 遷移自体は 3.3 の統合ロジック（useEffect）に任せる
};
```

- 呼び出し元（`RoomPage`）でゲームマスター判定を行ってから `room.handleQuickStart(users)` を呼ぶ形にする（権限チェックの責務は UI 側、実処理は hook 側という既存の分担に合わせる）。

### Step 5: `RoomPage.tsx` の権限チェック＆ボタン設置

```tsx
const myUserId = getUserId();
const isGameMaster = !!myUserId && myUserId === creatorId;

const onQuickStart = () => {
  if (!isGameMaster) {
    showToast('ルーム作成者のみが始めることができます。', { variant: 'error' });
    return;
  }
  room.handleQuickStart(users);
};
```

「お手軽スタート」ボタンを新規追加。押下可否そのものはUI無効化ではなくトースト通知で表現する（要件どおり）。

### Step 6: 自動遷移＆再入場救済の `useEffect`（`RoomPage.tsx`）

```tsx
useEffect(() => {
  if (status === 'WAITING' || status === '') return;
  const myUserId = getUserId();
  const isAnswerer = !!myUserId && myUserId === answerId;
  showToast('ゲームが始まっています', { variant: 'info' });
  router.replace(isAnswerer ? `/room/${roomId}/answer` : `/room/${roomId}/drawing`);
}, [status, answerId]);
```

- `router.replace` を使い、履歴に `RoomPage` を残して戻るボタンで無限ループしないようにする。
- これは「お手軽スタート押下直後の全メンバーの自動遷移」と「バック操作で `RoomPage` に戻ってきた時の復帰」の両方を1つのロジックで処理する（3.3節の方針）。

### Step 7: 画面レイアウト変更

要件のレイアウト案:
```
｜お手軽スタート|
｜絵を描く人はこちら|お題を答える人はこちら|
｜お題を変更する|
```

現状の [RoomPage.tsx](../components/pages/RoomPage.tsx) は縦積み（お題を変更する → DrawerGuideCard → AnswererGuideCard）。以下のように変更する:

1. 「お手軽スタート」ボタンをカード最上部（現在「お題を変更する」がある位置）に配置。
2. `DrawerGuideCard` と `AnswererGuideCard` を横並び（`grid grid-cols-2 gap-2` 等）にする。現状カードは `w-full` 想定のレイアウト（`Card` 内で `flex items-center justify-between` 等）なので、横並びにした際に文言・ボタンサイズが崩れないか要確認（レスポンシブ対応、モバイル幅では縦積みに戻すなど）。
3. 「お題を変更する」ボタンを最下部に移動。

### Step 8: `DrawPage` / `AnswerPage` 側のアナウンス表示（任意・補強）

Step 6 で `RoomPage` 経由の遷移にはアナウンスを出せるが、要件の文言「もしユーザーが描く人なら `DrawPage.tsx` にアナウンス後に遷移」を素直に読むなら、遷移先ページ側でも「ゲームが始まりました」的なトーストを一度出す実装（`DrawPage`/`AnswerPage` マウント時に `sessionStorage` 等でフラグを見て1回だけ表示）も検討可能。ただし `RoomPage`側で既にアナウンス後遷移しているため、**二重表示を避けるなら Step 6 のみで要件は満たせる**と判断する。ここは実装時に要件と相談して決定（4.6 未確定事項を参照）。

## 6. エッジケース・エラーハンドリング

- **参加者がゲームマスター1人のみ**: `handleQuickStart` で `members.length === 0`（自分を除く）or `=== 1`（自分だけ）の場合の挙動を決める必要あり。「自分自身が回答者になってもよい」のか「最低2人必要」で弾くのかは要件に明記が無いため要確認（4.6参照）。
- **`answer_id` が既にセットされている状態で再度押下**: `startQuickGame` は無条件に上書きする設計にしたため、二重押下や進行中ルームでの誤爆に注意。連打防止のため `handleQuickStart` 内でボタンの多重送信ガード（`isSubmitting` state）を入れることを推奨。
- **Presence の `users` に自分自身が含まれる**: `usePresence` の実装上、自分もトラック対象になるため `users` には自分も含まれる。ゲームマスター自身が回答者に選ばれるケースを許容するかは上記と同じ論点。
- **Presence接続前（`isConnected === false`）にボタンを押した場合**: `users` が空 or 不完全な可能性があるため、`isConnected` を見て抽選対象が揃うまでボタンを一時無効化する、または「参加者情報を取得中です」の表示を検討。

## 7. テスト観点

- ゲームマスターが「お手軽スタート」を押す → 回答者以外の全クライアントが `/room/{id}/drawing` に、回答者クライアントが `/room/{id}/answer` に自動遷移すること。
- ゲームマスター以外が押しても何も起きず、エラートーストが出ること。
- `DrawPage` 滞在中にブラウザバックで `RoomPage` に戻った際、ステータスが既に `DRAWING`/`ANSWERING` なら即座に元の画面へ戻されること（Step 6 のロジックがマウント時にも効くこと）。
- 参加者0〜1人時の挙動（4.6の結論に応じて分岐）。
- 既存の手動フロー（`DrawerGuideCard`/`AnswererGuideCard` からの個別開始）が引き続き動作すること（デグレ防止）。
